# 能力边界表

这张表不是「谁能做什么」的绝对划分，而是一条随能力增长而移动的**能力边界**。任何时候都要能回答：**我为什么让 AI 做这件事？**

---

## 一、可以交给 AI 的

| 类别 | 具体内容 |
| --- | --- |
| 知识检索 | 查资料、查 API、查文档、找 Demo、看源码入口 |
| 知识整理 | 归纳用法、对比方案、整理参数表、生成速查表 |
| 思路辅助 | 提供建议、寻找反例、指出遗漏的边界条件、列出风险 |
| 机械劳动 | 生成样板代码、格式化、批量重命名、重复结构铺开 |
| 局部产出 | 测试生成、局部实现、帮助重构、修简单 Bug |
| 执行提效 | 跑命令、写脚本、写测试脚手架、整理日志 |

---

## 二、必须由用户掌握的

| 类别 | 具体内容 |
| --- | --- |
| 业务 | 理解业务目的、流程、规则与边界 |
| 分析 | 问题拆解、现象到原因的定位 |
| 设计 | 方案设计、架构取舍、关键判断、重要 trade-off |
| 实现 | 复杂逻辑、并发、状态处理、异常处理、算法、易错核心路径 |
| 质量 | 结果验证、测试策略、验收标准 |
| 责任 | 对最终结果负责，包括向他人解释与承担后果 |

---

## 三、判定流程

面对任一子任务，按顺序自问：

1. 这件事**掌握在我脑子里**了吗？没掌握 → 属于闭卷区，我参与。
2. 它是否承载**认知价值**（学到新东西 / 形成新能力）？是 → 我参与。
3. 它是否只是**已理解的机械重复**？是 → 交给 AI。
4. 如果我把它交给 AI，**我还能判断结果对不对吗**？不能 → 我先补认知，再交出去。
5. 我为什么让 AI 做这件事？——**答不上来，就不要交出去。**

---

## 四、学习模式 vs 生产模式

同一件事，两种模式要求相反。混用是最大的错误来源。

| 维度 | 学习模式 | 生产模式 |
| --- | --- | --- |
| 目标 | 让能力进入大脑 | 效率、质量、结果 |
| 姿态 | 尽量闭卷 | 充分开卷 |
| AI 给什么 | 提示、引导、检查项、反例 | 实现、Demo、工具、现成方案 |
| AI 不给什么 | 完整答案、最终实现 | —（但仍不替我做判断与验证） |
| 允许慢吗 | 允许，慢是成本的一部分 | 不允许，慢是浪费 |
| 成功标准 | 今天学会了什么 | 今天交付了什么 |
| 典型动作 | 自己分析、自己写算法、自己 Debug、自己推导 | 查文档、看源码、搜 GitHub、问 AI、复制简单代码 |

**切换判断**：先问自己「这次是在培养能力，还是在使用能力？」
- 培养能力 → 学习模式
- 使用能力 → 生产模式

---

## 五、边界的演化

边界随能力增长而移动，不要把今天的策略固化成永久策略：

| 阶段 | 典型分工 |
| --- | --- |
| 新人（当前） | AI 给 API → AI 给 Demo → AI 给伪代码 → 我实现 |
| 成长中 | 我自己设计方案 → AI 补充知识 → AI 实现部分代码 |
| 成熟 | 我定义业务模型/架构/约束/验收标准 → AI 大量执行 → 我重点判断、验证、负责 |

要长期坚持的只有一条：

> **随着 AI 能力增强，我自己的能力也必须同步增强。**

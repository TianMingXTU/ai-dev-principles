# 交付前自检清单

把这份清单复制进项目（例如放到 `docs/review-checklist.md`），每次交付前过一遍。

判定标准不是「是不是我写的」，而是——**我是不是理解这段代码？**

---

## A. 业务层（思考闭卷区）

- [ ] 我能说清这个需求真正要解决什么问题，以及不做的后果
- [ ] 我能画出正常路径的流程
- [ ] 我能说出全部业务约束、权限、状态机规则
- [ ] 我能说出输入输出的来源与格式
- [ ] 我能列出边界：异常、超时、重复、并发、空值、数量级上限

## B. 方案层（思考闭卷区）

- [ ] 我理解为什么选这个方案
- [ ] 我说得出至少一个被否掉的备选方案，以及否掉的理由
- [ ] 我知道这个方案的主要风险在哪
- [ ] 关键 trade-off 是我自己拍的板，不是我照抄的结论

## C. 实现层

- [ ] 我逐行看过这段代码，而不是略读
- [ ] 我知道每一处 API 调用为什么需要、参数为什么这么传
- [ ] 标了 `[复杂]` 的部分是我自己实现的，或至少是我自己研究过再接受的
- [ ] 没有残留「我不确定但先这样」的段落
- [ ] 异常处理、并发、状态处理我看懂了，不是照抄

## D. 验证层

- [ ] 我知道怎么测试这个功能
- [ ] 我实际跑过，或者明确知道该跑什么
- [ ] 我知道出问题时从哪里开始排查
- [ ] 我能向同事解释这段代码
- [ ] 我愿意对它的最终结果负责

## E. 规模层（审核带宽）

- [ ] 单次接受的代码量在我的审核带宽内（参考：≤ 50 行舒适，> 150 行需要拆分）
- [ ] 没有一次性接受一个庞大功能然后只看最终结果
- [ ] 每一块都是「小步实现 → 小步验证 → 确认 → 下一块」

---

## 通不过怎么办

| 通不过的项 | 处理方式 |
| --- | --- |
| A / B 类 | 停下来，重新理解业务和方案，不要继续写 |
| C 类 | 让 AI 就那一点补讲，直到能自己复述 |
| D 类 | 先补测试与验证，再往下走 |
| E 类 | 立即拆分，回退到上一块的结尾重新推进 |

## 最后一句

> 今天不会的东西，经过一次真实项目以后，逐渐变成我的能力。
>
> 可以不理解全部，但不能接受「做完需求以后，还是不知道它为什么这样做」。
